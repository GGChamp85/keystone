# Changelog

All notable changes to this project are documented here. Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versioning follows [Semantic Versioning](https://semver.org/).

## [Unreleased]

Platform foundation — self-hosted, air-gapped LLM inference gateway and autonomous coding agent platform:

### Added
- **Keystone Inference**: OpenAI-compatible gateway (`/v1/chat/completions`, `/v1/models`), API key management, rate limiting, token budgets, subscription tiers, multi-model routing (coding/coding_fallback/reasoning) with health-aware fallback and per-tenant adapter resolution.
- **Keystone Agents**: LangGraph Plan→Code→Quality→Review→Test→Fix background agent with real tool use (read/grep/run/patch, not full-file rewrites), a real git workflow (clone → branch → commit → push → PR against a real Gitea), Temporal-backed durable execution, and a live plan/execution-trace web UI (`web/`, React SPA served at `/app`) streaming progress over Server-Sent Events.
- **Multi-developer + scale**: user/role identity (`admin`/`lead`/`developer`) on every task and memory action; a Redis-backed per-tenant/per-user concurrency limiter; automatic PR-status polling into `task_feedback`; incremental, AST-aware, per-tenant repo indexing for large repos/monorepos.
- **Memory system**: a per-repo/per-tenant memory the agent learns from and a human can inspect, pin, approve, and forget — exposed via `keystone memory ...`, the web UI's Memory panel, and an OpenCode plugin/MCP server.
- **Fine-tuning, end to end**: real training-data sources (git history, accepted-task trajectories, repo pretraining text), a stratified train/holdout manifest with real content hashes, eval-aware LoRA/SFT/DPO trainers, an adapter registry with promote/rollback, LoRA-serving vLLM flags, adapter-aware routing through every real inference call site, a Temporal-backed job runner with an asyncio fallback, a full `/v1/finetune` REST API, `keystone finetune ...` CLI commands, and a 3-step web wizard (pick data → start → verdict).
- **Distributed model serving**: per-role horizontal replica scaling behind a load-balanced Service, real multi-node pipeline-parallel serving via vLLM's Ray executor for models too large for one GPU node, and KEDA-based autoscaling on the real `vllm:num_requests_waiting` metric — all three paths rendered and verified in CI via `helm lint`/`helm template`.
- **Real, non-mocked benchmark harness** (`benchmarks/`): scores a model's completion by actually executing it in a real sandbox (gVisor) — no LLM-as-judge — with a real token-cost comparison against gated frontier clients (Anthropic/OpenAI, only constructed when a real API key is present). Run for real against `claude-opus`/`claude-sonnet` in this repo's own development environment; see the README's benchmark section for the actual numbers.
- **Real repo-task agent benchmark** (`benchmarks/agent_runner.py`): the actual agent loop — `src/orchestrator/engine.py`'s real engine, real tools, real quality gates — run against a seeded real Gitea repo with a real bug and a real failing test, end to end. `benchmarks/frontier_proxy.py` (new) makes a real frontier model usable as a coding-role backend by translating `src/inference/client.py`'s exact wire protocol to and from the real Anthropic Messages API — no changes needed to `InferenceClient` or any orchestrator node. Run for real: the `token_bucket` task was solved by the frontier model in 67.6s across 5 real iterations (plan → tool-based fix → quality gates → review → tests → push → PR), independently confirmed by cloning the pushed branch in a fresh sandbox and re-running both held-out tests.
- **Self-hosted sandboxing**: Firecracker microVMs (primary) with an automatic gVisor fallback where KVM isn't available; host-side-only network egress enforcement.
- **Air-gap packaging**: offline bundle scripts for container images, Python wheels, npm packages, and model weights; a real internal CA (`pki/`); verified zero-egress runtime for the core stateful stack.
- **Observability**: Prometheus, Grafana (3 real dashboards), Loki, Promtail, and Alertmanager with 6 real alert rules — deployed and verified on both docker-compose and a live Kubernetes cluster.
- **Infrastructure**: Kubernetes/Helm chart (client-VPC production tier) and OpenTofu modules (RunPod dev/test tier); NetworkPolicy-segmented tiers; OpenBao-backed secrets with a real init/unseal/seed lifecycle.
- **Compliance**: full third-party license inventory (`docs/LICENSES_AND_COMPLIANCE.md`) and telemetry audit (`docs/TELEMETRY_AUDIT.md`), including catching and fixing a Redis relicensing issue (switched to Valkey) before it shipped.
- **`keystone doctor`**: real diagnostics against Postgres, Redis, Qdrant, the sandbox daemon, every model endpoint, the git host, package mirrors, and secret strength — connects to configured infrastructure directly, so it works even before the app itself is up, and reports exactly what's wrong rather than a bare pass/fail.
- **`keystone init`**: guided setup that writes a real, working `.env` from `.env.example` with strong random secrets generated by default, and can interactively configure a git host and pick between a self-hosted GPU backend or `benchmarks/frontier_proxy.py`.
- **`keystone tenants create`/`keystone users add`/`list`/`keystone keys-create`**: real CLI wrappers around the existing root-admin-token-gated `/v1/admin` routes — the first CLI-based bootstrap path for tenants/users/API keys this project has had.
- **`keystone up`/`down`/`bundle download-models|build-images|import`**: real subprocess wrappers (stdout/stderr inherited, real exit codes propagated) around `docker compose` and the existing `airgap/*.sh` scripts — verified for real, not just that the constructed command looked plausible.
- **`keystone ingest`**: a real CLI wrapper around the existing `POST /v1/keystone/ingest` route (`src/memory/ingestion.py`'s `CodeIngestionPipeline`) — repo ingestion no longer needs to be triggered indirectly through a coding task. Run for real against a live server and a real public GitHub repo: the first run processed 23 files into 61 chunks; a second run against the same commit correctly reported all 23 files unchanged and 0 chunks re-created, proving the incremental skip path.
- **`benchmarks/eval_prompt.py`**: an ad hoc single-input eval — run one arbitrary prompt (optionally with a real test) through Keystone Inference and any configured frontier models side by side, without writing a `benchmarks/tasks/*.json` file first. Reuses the same real sandbox scoring path and cost model as the fixed task suite. Run for real: both unscored (raw completions) and scored (a real ad hoc test, real sandbox pass/fail) modes verified end to end against a live sandbox and a live Anthropic API.
- **PII redaction at the frontier-model boundary** (`src/security/pii_redaction.py`): real, deterministic detection of email/phone/SSN/credit-card (real Luhn checksum)/IPv4 patterns, wired into `benchmarks/frontier_proxy.py` behind an explicit opt-in (`FRONTIER_PROXY_REDACT_PII=1`) — the one real point where request content leaves the self-hosted network for a third-party API. Verified for real against a live request: with the flag on, a real email/phone were confirmed redacted before reaching the frontier model (via the proxy's own logs); with it off, the same real value round-tripped through the model unchanged.
- **Task-complexity-aware model routing**: `AgentTaskRequest.model` accepts `"auto"`, resolved once by `src/inference/model_router.py`'s real heuristics (`classify_task_to_role` for reasoning vs. coding, and — opt-in via `TASK_COMPLEXITY_ROUTING_ENABLED=1` — `classify_task_complexity` for simple vs. complex within coding) before the task is persisted, so the resolved role is always visible in `AgentTask.model_role`, never a hidden live decision. Deliberately conservative: an ambiguous or unmatched task defaults toward the more capable model, not the cheaper one. Verified for real: submitting a task with `model="auto"` against a live Postgres/Redis correctly persisted `reasoning` for a review-flavored description and `coding_fallback` for a "fix a typo" description with the flag enabled.
- **Prompt-injection defense on every tool result** (`src/security/prompt_injection.py`): every successful tool result the coding agent reads — file contents, grep matches, command output — is wrapped in an explicit `<tool_output tool=... detail=...>` untrusted-data delimiter naming its real source (spotlighting) before it re-enters the model's context, and real regex detection for common injection phrasings ("ignore previous instructions", role overrides, system-prompt exfiltration, named jailbreak personas) adds a visible security notice inside that specific result on a match. Content is never altered or dropped, so unlike PII redaction this is on by default. The detail attribute is HTML-escaped and length-capped so a quote inside a real shell command can't forge tag syntax. Defense in depth, honestly scoped: a disguised injection can still evade the patterns.
- **A real, no-GPU model backend for CI and laptops** (`demo-model` compose profile, `make up-demo`): llama.cpp's server pulling the official Apache-2.0 Qwen2.5-Coder-0.5B-Instruct GGUF (676 MB, cached after the first run) — a real OpenAI-compatible endpoint with `/v1/models`, tool calling (`--jinja`), streaming with usage, and JSON-schema output, so every model-dependent test can run for real instead of self-skipping. CI now starts it for the whole test job and caches the GGUF across runs. `tests/e2e/test_ci_backend.py` verifies health, a real completion with real token usage, and real streaming against it. Probed for real through the same client: JSON-schema structured output (`chat_structured`) returns schema-conformant JSON on this model; native `tool_calls` do not come back reliably — it emits the call as a fenced JSON block in the message content instead, which is the shape the existing text tool protocol (`src/orchestrator/tools/protocol.py`) parses, so that is the protocol the demo role uses for agent-loop tests. What it does not claim: a 0.5B model's answer quality — that comes from the GPU tiers and the benchmark suite.
- **A real trainer run in CI** (`docker/training.Dockerfile`, `tests/test_trainer_smoke.py`, CI job `train-smoke`): a Python 3.12 training image with CPU torch and the `finetuning` extra — pinned to 3.12 on purpose, since the ML stack lags the newest CPython and the main app's own venv runs an interpreter where these wheels aren't installable — and a test that trains a real LoRA adapter on the real Qwen2.5-Coder-0.5B-Instruct on CPU (two optimizer steps, a real held-out `eval_loss`), saves it, and reloads it with PEFT for continued training. The first trainer execution this repository has ever had; it immediately caught two real trainer bugs (see Fixed). A smoke, not a training claim.
- **`LoRATrainingConfig.max_steps`**: a hard optimizer-step budget that overrides `num_epochs` — what a bounded smoke run and a cost-estimated guided run both need.
- **Per-role bearer tokens** (`VLLM_*_API_KEY`) so a hosted OpenAI-compatible endpoint such as RunPod Serverless can serve a role, plus `RUNPOD_API_KEY`/`RUNPOD_ENDPOINT_URL` settings and a `keystone doctor` check that distinguishes unconfigured, half-configured, and unreachable from a real authenticated round trip. The fake vLLM test fixture records request headers so the token is proven to reach the server.
- **`keystone deploy runpod-serverless`** (`src/cli/runpod_serverless.py`): a real client for RunPod's REST API that stands up a serverless vLLM endpoint (RunPod's maintained `worker-v1-vllm` image) serving an open-weight model — default Qwen2.5-Coder-7B-Instruct on the 24GB tier — scaled to zero when idle, so a GPU backend costs $0 until the first request. Idempotent by name (re-running reuses the existing template/endpoint rather than creating billable duplicates); `--destroy` tears both down. Request shapes are asserted against RunPod's published OpenAPI document, not guessed. REST rather than OpenTofu because the provider ships no template resource and an endpoint requires one. Run for real: the template was created; endpoint creation was refused by RunPod with an HTTP 500 whose body says the account has $0 credit — now translated into a plain instruction (add credit, re-run) instead of a raw error, with that exact real response body as the test fixture. `docs/deployment/RUNPOD_SETUP.md` now leads with this path.
- **Repository map for the coding agent** (`src/orchestrator/repo_map.py`, tool `get_repo_map`): the planner and the coding loop now start from a ranked outline of the whole repository — every class/function/method/type with file, line and signature, most-referenced code first, within a token budget — instead of a blind `find -maxdepth 2`. Built inside the task's real sandbox by universal-ctags (one apt package in the sandbox image, every language the agent meets; not tree-sitter, whose grammar wheels would have to ride in the air-gap bundle — ADR 0001) plus one `grep -F` pass that counts how often each symbol name is used, so a file whose symbols are called from everywhere ranks above a leaf. The map is built once per task right after the clone (the planning node now clones, so the plan names real files) and cached on the state; if ctags is missing from a custom sandbox image the map degrades to a labelled file list rather than silently disappearing. Verified for real: ctags ran inside a live sandbox and produced the expected symbols, signatures, line numbers and reference counts (`tests/test_repo_map.py`).
- **`read_file` line ranges** (`start_line`/`end_line`, numbered output) so the agent reads the region the map pointed at instead of whole files, and **fuzzy `apply_patch`**: a `search` block that differs from the file only in whitespace/indentation, or is ≥92% similar, is applied when — and only when — it matches exactly one place; the result says a fuzzy match was used and where. Two candidate places are refused as ambiguous, never guessed (`tests/test_fuzzy_patch.py`, real-sandbox cases in `tests/test_tool_impl.py`).
- **The agent installs the repo's dependencies and verifies its own work**: `repo_profile.install_cmd` was detected but never executed — the repo's real test suite ran against a bare sandbox. It now runs once per task right after the clone (`nodes/_shared.py::install_dependencies`, pointed at the configured `PIP_INDEX_URL`/`NPM_CONFIG_REGISTRY`/`GOPROXY` mirrors, fail-fast retries), and a failed install is recorded on the state and shown to the coding model so a `ModuleNotFoundError` is attributed to the install rather than mistaken for the model's bug. The testing node runs **related tests first** (`src/orchestrator/test_scope.py`: pytest modules matching the touched files' stems, jest `--findRelatedTests`, `go test` on the touched packages), then the full suite only once those pass — targeted failure output instead of a wall of unrelated tests. A new **`run_tests` tool** (`scope='related'|'all'`) gives the model the same runner mid-loop, and the system prompt now tells it to verify before signaling done instead of discouraging it. Found on the way: a Python repo identified only by `pytest.ini`/`tox.ini`/`conftest.py` was classified as an unknown ecosystem — fixed, with no install step for a repo that has nothing to build. All verified against a real sandbox: a real `pip install -r requirements.txt` succeeding and failing (the failure text attributed), and real pytest runs — related, full, "no related tests → full", and a genuine failure returned as information rather than a tool error.
- **Streamed coding turns** (`InferenceClient.stream_to_message`): every turn of the agentic loop now streams — tool calls and text are reassembled from OpenAI-style deltas into the same response shape `complete()` returns, with real token usage from the `stream_options.include_usage` final chunk (verified against a live llama.cpp server) and an `on_text` callback for live progress. Retries apply until the first chunk arrives; a stream that has started is never replayed. The fake vLLM fixture now serves real SSE (a tool call whose JSON arguments are split across chunks), and the frontier proxy emits a tools request as a well-formed chunk sequence instead of dropping the tool calls. `AGENT_STREAM_TURNS=0` restores blocking requests for a backend that cannot stream tool calls.
- **Summarise-on-overflow instead of drop-on-overflow** (`context.trim_turns_to_budget_async`): when the loop's conversation exceeds `AGENT_MAX_CONTEXT_TOKENS`, the oldest turns are condensed by the cheaper `coding_fallback` role into a "Context summary" the model keeps — files read and what was learned, edits applied, results seen — rather than a bare "N turns were dropped". Falls back to the plain notice if the summariser fails; a summary is never the reason a task fails.
- **Configurable quality-gate strictness**: `QUALITY_GATE_BLOCKING_TOOLS` (default `bandit`, `mypy`) and a per-task `quality_blocking_tools` on `AgentTaskRequest`, carried through the Temporal workflow input — list `ruff`/`eslint`/`tsc`/`go`/`cargo` to make lint findings send the task back to fixing. bandit's low-severity findings stay informational even when it blocks.
- **Streaming requests are billed for real**: the gateway's streaming path counted ~1 token per SSE chunk and never counted the prompt. It now always asks the backend for `stream_options.include_usage` (vLLM and llama.cpp both honor it), records the backend's real usage from the final chunk (forwarding that chunk to the caller only when the caller asked for it, as an OpenAI client that did not may not expect a chunk without choices), and — if a backend sends no usage at all — counts prompt and completion tokens with the agent's own tokenizer and logs that it is an estimate. Both paths now label usage metrics with the model role.
- **A real live trace** (transparency): the task event stream carried one summary per graph node; it now also carries every step *inside* a node as it happens — `tool_call`, `tool_result` (the whole output), `model_text`, `test_output` (the whole stdout/stderr), `quality_findings`, `deps_install`, `repo_map`, `route_decision`, `diff`, `pr` — with full payloads and no stream trimming (the previous `MAXLEN 500` silently dropped a long task's earliest steps). The same steps are persisted on each `IterationRecord` in the task's execution trace, so the record in Postgres is as complete as the live feed. The stream now closes on the engine's `final` event, published after the commit/push/PR rather than at the graph's terminal phase, so a viewer sees the diff and the pull request before the connection ends. The web trace view gained the quality phase and a "Live steps" log with expandable bodies (tool output, test output, diff) and shows the PR link and commit on completion. Verified against a real Redis: 1,200 steps read back complete and in order, a 250 kB tool output intact.
- **No policy limits and no lossy truncation anywhere** (production posture): every budget is now 0 = unlimited by default — tenant daily/monthly tokens (were 5M/100M), the gateway's per-key request rate (was 60/min), `MAX_TOKENS_PER_REQUEST` (was 32,768), the per-task token cap (was 2M), the whole-task wall clock (was 30 min) — and `max_iterations` lost its ceiling of 50 (it remains the one per-task *safety* bound, set per task). Timeouts for the repo's tests, dependency install, quality tools and `run_command` are now generous, configurable settings instead of 180–600 s constants. Every fixed-size slice on persisted data is gone: test output and errors, quality findings, the task diff (was cut at 200 kB), install logs, git-host/sandbox error messages and trace records are kept in full; the commit message and PR body carry the complete task description (only git's 72-character subject convention and Gitea's 255-character title limit apply, both external). The single remaining truncation is fitting text into one model prompt — `context.fit_to_tokens`, budgeted from `AGENT_MAX_CONTEXT_TOKENS` rather than any fixed byte count, keeping the tail of test output (where the failures are) and the head of files/diffs, and stating exactly how much was omitted and where the full text lives.
- **No concurrency cap by default** (multiple developers, multiple repos, in parallel): `Tenant.max_concurrent_agents` defaulted to 3 with no API to change it, so every tenant's fourth concurrent task was rejected with HTTP 429 — a policy number standing in for capacity. The column now means 0 = no cap (the new default; migration `6a1c2f9e0b3d` moves rows still holding the old default of 3 to 0), the sandbox daemon's per-tenant cap follows the same rule (`SANDBOX_MAX_CONCURRENT=0`), and a positive cap is a deliberate admin choice via `POST /v1/admin/tenants` `max_concurrent_agents`, still enforced with per-user fairness when set. Each task already runs in its own sandbox, own clone, own branch and own PR, so nothing serialises on a repository; throughput is bounded by the worker, sandbox and GPU capacity you deploy (Temporal workers and sandbox daemons scale horizontally; vLLM autoscaling is KEDA-driven).
- **Static type checking in CI** (`mypy src/`, zero errors, enforced in the lint job): `src/db/models.py` converted from classic `Column(...)` declarations to SQLAlchemy 2.0 `Mapped[...]`/`mapped_column(...)` so every ORM attribute carries its real Python type — that one change took the baseline from 236 errors to 102, and the rest were fixed at the source rather than baselined: nullable columns handed to non-optional response fields, `Optional` values passed unchecked into git-host and sandbox calls, a budget comparison against a possibly-unset limit, and a graph builder annotated as returning the uncompiled graph. Nullability was preserved exactly through the conversion (`alembic check` reports no drift), then made honest where the code already assumed a value: migration `519d4719f677` backfills and declares `created_at` on every table, `api_keys.scopes`, `finetune_jobs.status`, and `codebase_indexes.chunk_count` NOT NULL. Verified for real: a row inserted outside the ORM with a NULL `created_at` was backfilled by the migration, the constraint held, and downgrade/upgrade round-tripped clean; the full suite (438 tests) passed against the migrated schema.

### Fixed
- **The sandbox's egress firewall never actually allowed a deployment's real configured `GIT_ALLOWED_HOSTS`** — only the hardcoded placeholder `*.internal.keystone.local` hostnames, regardless of what an operator set. A custom git host correctly passed the SSRF allowlist check (`_validate_repo_url`) and then had its real `git clone` silently blocked by egress DENY, completely breaking the README's own "Connect your own git server" instructions for anyone who followed them. Found and fixed by actually running `tests/test_git_workflow_integration.py` end to end against a live Gitea for the first time — `build_egress_policy()` now wires the real configured git/mirror hosts into real ALLOW rules.
- **`docker-compose.yml`'s sandbox network had no pinned name**, so Compose silently prefixed it with the project name; every network-enabled sandbox (any git operation) then failed outright with a real 404 from the Docker API. Same discovery pass as above.
- **`tests/test_cli_doctor.py` hardcoded this dev machine's own local port numbers** instead of reading `DATABASE_URL`/`REDIS_URL`/`QDRANT_HOST`/`QDRANT_PORT` from the real ambient environment like every other integration test — passed locally by coincidence, broke `main`'s real CI for several commits (different service-container ports there) before a direct check of the GitHub check-runs API — not just `gh run watch`'s reported exit code, which had been giving false "success" signals for runs that were actually being cancelled by rapid sequential pushes — caught and fixed it.
- **The `/v1/keystone/ingest` route never caught `InvalidRepositoryURLError` or a failed `git clone`**, so a disallowed host or a nonexistent branch surfaced to the caller as an opaque 500 instead of the real reason — found by actually running `keystone ingest` against a disallowed host and a bad branch, not just the happy path. Now mapped to a clean 400 with the actual error message.
- **The circuit breaker had no limit on consecutive quality-gate failures** — the quality node could route CODING → QUALITY → FIXING indefinitely, bounded only by the iteration and token budgets. `CircuitBreakerConfig.max_consecutive_quality_failures` (default 3) now trips it like the test and review limits do.
- **`MAX_TOKENS_PER_REQUEST` was a dead setting** — defined in `src/config.py`, referenced nowhere. `/v1/chat/completions` now rejects a request above the deployment's ceiling with a 422 before routing, instead of passing anything up to the protocol maximum through to the model.
- **The fake vLLM test fixture could error at setup on a slow CI runner** — its readiness probe caught only `httpx.ConnectError`, so a `ConnectTimeout` during uvicorn's bind escaped as a fixture error rather than a retry (seen for real in CI). It now retries on any `httpx.TransportError`.
- **Removed dead code**: the batch inference queue (`src/inference/batch.py`, `batch_worker.py`) had no HTTP route and no worker deployment; `AgentState.cumulative_diff`, `max_review_retries`, and `max_test_retries` were never read (the real limits live in `CircuitBreakerConfig`).
- **All three trainers passed `warmup_ratio` to `TrainingArguments`, which transformers 5.x removed** — a `TypeError` on the first real run, invisible for as long as no test executed a trainer; `pyproject.toml` pins `transformers>=4.44` unbounded, so CI would have hit it too. `src/finetuning/_common.py`'s `warmup_kwargs` now resolves the right keyword from the installed class's real signature: `warmup_ratio` on 4.x, `warmup_steps` as a float ratio on 5.x (identical semantics), rather than pinning the ecosystem back.
- **The LoRA trainer forced model weights to float16 even with `fp16=False`** — the dtype is now tied to the requested mixed-precision mode, so a CPU run (neither fp16 nor bf16) loads float32 instead of failing.
- **transformers 5.x's threaded weight loader segfaults on macOS arm64** (`core_model_loading._materialize_copy`, torch 2.14 / transformers 5.17, observed with a real fault stack) before any training code runs. The smoke test sets transformers' own `HF_DEACTIVATE_ASYNC_LOAD` switch; the trainer itself is untouched.
- **Documentation now says only what the code does**: the README's `"status": "ok"` health example (the code emits `"healthy"`), an unbacked claim that a CPU LoRA smoke run had proven the trainer path (at the time, no automated test had ever executed a trainer — one now does, see Added), a stale `model_router.py` docstring saying adapter routing wasn't wired into the orchestrator nodes (it is), and a SUPPORT.md line written before `keystone doctor` shipped. Vendor model names are no longer used in repo-facing text; cost reports use vendor-neutral tier labels.

### Known limitations (tracked, not hidden)
- Model-quality behavior on Keystone's own self-hosted models (the actual LLM output) is unverified in this codebase's development environment, which has no GPU — see `docs/deployment/KUBERNETES_CLIENT_VPC.md` for what's verified vs. GPU-gated.
- No adapter has been fine-tuned on real GPU hardware yet, and fine-tuning's "only promote if it beats base+RAG" auto-verdict gate isn't wired up — promotion is a manual decision today.
- The full multi-file-repo benchmark suite has only one real task (`token_bucket`) — the phase calls for 10-20, plus a persisted comparison sweep (base / base+RAG / fine-tuned / frontier) and a web UI panel, none of which exist yet.
- See `ROADMAP.md` for the full phase-by-phase status, including what's checked and what each checked phase's known gap still is.
