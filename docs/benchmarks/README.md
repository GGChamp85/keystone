# Benchmarks

**What they answer.** Does the agent actually fix real bugs in real repositories, how often, at what cost, and how does a self-hosted open-weight model compare with a frontier model behind the same pipeline? Every number here comes from executing code in a real sandbox and reading the real exit code. There is no model-as-judge anywhere.

## Two harnesses

| Harness | What it runs | Use it for |
|---|---|---|
| `benchmarks/agent_runner.py` | the **whole agent loop** on a seeded repository task: plan, tool-based coding, quality gates, review, tests, push, pull request; then a fresh clone re-runs the held-out tests | the real question: does the agent deliver a mergeable fix |
| `benchmarks/run_benchmark.py` | single-function completions scored by executing them in a sandbox, with a token-cost comparison | a fast smoke of a model or a prompt; `benchmarks/eval_prompt.py` does one prompt ad hoc |

## The repository tasks

Twelve tasks under `benchmarks/tasks/repo/`, each a small real repository with a genuine bug, a failing test that the fix must make pass (`fail_to_pass`) and tests that must keep passing (`pass_to_pass`). Each task proves its own premise in CI: `tests/test_repo_tasks_well_formed.py` checks that the held-out tests really fail before the fix and really pass after — Python with pytest, Node with the built-in test runner, Go with `go test` inside the Go sandbox runtime image.

Python: `backoff_cap`, `config_deep_merge`, `csv_quoted_fields`, `date_range_inclusive`, `inventory_negative_stock`, `lru_cache_recency`, `pagination_last_page`, `slugify_collapse`, `token_bucket`. Node: `slug_dedupe_node`, `retry_jitter_node`. Go: `lru_ttl_go`. The agent runs each in the sandbox runtime image for its ecosystem (`docker/sandbox-runtimes/{python,node,go}.Dockerfile`, chosen after the clone from the repository's own tooling).

## Run it

```bash
python -m benchmarks.agent_runner --task token_bucket --max-iterations 8            # one task
python -m benchmarks.agent_runner --persist --backend-label coding                  # all tasks, rows into benchmark_runs
python -m benchmarks.compare --backend base=http://vllm:8000/v1 --backend frontier=http://localhost:8090/v1
python -m benchmarks.report                                                          # -> docs/benchmarks/latest.md
```

Requirements: a git host the agent may push to (a local Gitea works), the sandbox daemon, and a model behind the coding role: your GPU, the CPU demo model (plumbing only), or a frontier model through `benchmarks/frontier_proxy.py`.

## Real results so far

- The `token_bucket` task (a rate limiter whose refill did not cap at capacity) was solved by a frontier model through the unmodified agent loop in **67.6 seconds over 5 iterations**: planning, tool-based edits, quality gates, review, tests, a real push and a real pull request, confirmed by re-running both held-out tests in a fresh sandbox clone.
- The single-function smoke suite, run from a development machine with no GPU: the self-hosted role reported an honest 0/3 (no endpoint reachable, not a fabricated score); two frontier models scored 3/3 with real sandboxed execution.

## The comparison in the web UI

**Benchmarks** in the web UI (`GET /v1/keystone/benchmarks`) shows the same rows as a comparison: per backend, how many tasks were solved, the average time and the tokens spent; per task, the latest run of every backend with its status, duration, tokens and pull request link. It is empty until a run has been persisted.

## What is not published yet

No sweep has been run on GPU hardware, so `docs/benchmarks/latest.md` is generated by `benchmarks/report.py` from the `benchmark_runs` table and not published until it comes from a real GPU run. Cost per solved task is computed by `benchmarks/cost_model.py` from **your** measured throughput and GPU price, never a vendor's claim.

Throughput and latency under load are a separate question, answered by the [load test](load-test.md).
