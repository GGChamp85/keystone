# Roadmap

Public tracking of where Keystone is headed. Tracks the phased plan for bringing Keystone Agents to Codex/Cursor-class quality with company-specific fine-tuning that measurably beats plain RAG. Each phase ships behind config flags with its own tests; phases are independently shippable.

A checked box means the phase's real, testable scope is done and covered by real tests against real infrastructure (Postgres/Redis/Qdrant/sandbox/git host) — not that every GPU-dependent behavior has been observed on real hardware, since this project's own development environment has no GPU. Each phase's status line says exactly what that gap is where one exists; nothing here is checked on the strength of code that has never actually run.

- [x] **Phase 0 — GLM-5.3-Flash model support**: GLM-5.3-Flash (zai-org, MIT) is the default coding model, Qwen2.5-Coder-32B-Instruct the fallback; vLLM bumped for MoE + native tool-calling, tool-parser flags verified against vLLM's real parser registry. *Config/infra complete and unit-tested; the actual tool-call round-trip against a live GLM endpoint (`scripts/smoke_glm_toolcall.py`) needs real GPU hardware to verify.*
- [x] **Phase 1 — Real git workflow**: the background agent clones the real repo into its sandbox, runs the repo's real test suite, commits to a branch, and opens a pull request against a real Gitea instance — not a JSON blob of file contents. Verified by actually running `tests/test_git_workflow_integration.py` end to end against a live Gitea 1.22 container, a live sandbox daemon, and a live gVisor sandbox (this test has real infra requirements and, as far as this project's history shows, had never actually been executed before) — doing so surfaced and fixed two real bugs no mock would have caught: the sandbox's egress firewall never actually allowed a deployment's real configured `GIT_ALLOWED_HOSTS`, only the placeholder default hostname, silently breaking the README's "Connect your own git server" path for anyone who configured it; and `docker-compose.yml`'s sandbox network had no pinned name, so Compose's project-name prefixing made every network-enabled sandbox fail outright.
- [x] **Phase 2 — Agentic loop engineering**: tool use (read/grep/run/patch) inside the coding loop instead of single-shot full-file rewrites; a review gate that fails closed; re-planning after repeated failures; context budgeting for large diffs.
- [x] **Phase 3 — Quality gates + memory**: enforced lint/typecheck/security scanning before review; a per-repo and per-tenant memory system the agent learns from and a human can inspect, pin, and forget — exposed via `keystone memory ...`, the web UI's Memory panel, an OpenCode plugin, and the VS Code extension. Retrieval is hybrid (vector + Postgres full text, fused) over structure-aware chunks; memory recall ranks by full-text rank.
- [x] **Phase 4 — Multi-developer + large-repo scale**: user/role identity (`admin`/`lead`/`developer`) on every task and memory action, a Redis-backed per-tenant/per-user concurrency limiter, automatic PR-status polling into task feedback, and incremental AST-aware, per-tenant repo indexing for monorepos.
- [ ] **Phase 5 — Fine-tuning that beats RAG**: real, tested infrastructure end to end — three data sources (git history, accepted trajectories, repo pretraining text), a stratified train/holdout manifest, eval-aware trainers, an adapter registry with promote/rollback, LoRA-serving vLLM flags, adapter-aware routing through every real inference call site (including the OpenAI-compatible gateway), a Temporal-backed runner with an asyncio fallback, a full REST API, `keystone finetune ...` CLI commands, and a 3-step web wizard. The guided "describe → plan & cost → approve" path is now built and verified end to end (`keystone finetune guided`, `POST /v1/finetune/plans`, the web wizard; `docs/guides/fine-tune-slm-on-your-repo.md`): real commits and accepted tasks → a sanitised, repository-stratified dataset → a plan from the SLM catalog and the detected GPUs → a `planned` job → approval → the runner. The verdict gate is wired: the trainer evaluates the untouched base model on the held-out split before training and the adapter after, `src/finetuning/verdict.py` compares them, and `promote` refuses a `fail`/`unknown` verdict (409) unless an admin forces it (audited); a promoted adapter is written to the `lora_modules.json` manifest and live-loaded into vLLM (`src/inference/lora_registry.py`), and training progress streams per step. An adapter can now be **exported** (`keystone finetune export`, `POST /v1/finetune/jobs/{id}/export`): merged into the base weights, converted to GGUF with llama.cpp's converter, or AWQ-quantised — the merge and the GGUF conversion run for real on the CPU smoke's adapter. Where a job trains is a setting (`FINETUNE_BACKEND`): in process, on a **KubeRay** cluster as a Ray Train job (ADR 0002 implemented — `src/finetuning/backends/ray_train.py`, the chart's `RayCluster`; the Kubeflow runtime is gone), or on a rented **RunPod pod** whose adapter lands on a network volume (ADR 0005). *Still open: the verdict compares held-out loss only — the planned base+RAG task-level comparison via `benchmarks/compare.py` is not part of it yet; no adapter has been trained on a real GPU (the trainer itself is executed for real in CI — `tests/test_trainer_smoke.py` trains a LoRA on the 0.5B model on CPU with a real held-out eval loss — but that is a smoke, not a training claim); the AWQ export needs a CUDA GPU and has not run; the Ray backend's `TorchTrainer` configuration is unit-tested and constructs the real Ray objects, but no job has run on a real Ray cluster; the RunPod pod backend's request shapes are asserted against RunPod's OpenAPI document and its loop runs against a local server, but no pod has been launched — the RunPod account has no credit.*
- [ ] **Phase 6 — Benchmarks + eval, including frontier models**: two real, complementary harnesses now exist. `benchmarks/run_benchmark.py` is a small 3-task single-function harness (real sandbox-executed pass/fail, no LLM-as-judge, real token-cost comparison). `benchmarks/agent_runner.py` is the real thing this phase actually calls for: a repo-scale task run through the *actual* agent loop — plan, real tool-based coding, quality gates, review, tests, a real git push, a real PR — not a free-standing completion. `benchmarks/frontier_proxy.py` (new) is what makes a frontier model usable as a real coding-role backend at all: a real OpenAI-compatible translation layer in front of the real Anthropic API, so `src/inference/client.py`'s unmodified `InferenceClient` — the exact class every orchestrator node already uses — can talk to a frontier model with no changes to the orchestrator. Run for real end to end against a live Gitea, a live sandbox, and a frontier model: the seeded `token_bucket` repo task (a real bug, a real failing regression test) was solved in 67.6s across 5 iterations, independently confirmed by cloning the pushed branch in a fresh sandbox and re-running both held-out tests. Now nine repo tasks (each proven honest by `tests/test_repo_tasks_well_formed.py`: the held-out tests really fail before the fix and really pass after), persistence (`benchmark_runs`, written by `agent_runner.py --persist`), a comparison sweep across backends (`benchmarks/compare.py`) and a report regenerated from the rows (`benchmarks/report.py` → `docs/benchmarks/latest.md`). *Still open: the tasks are Python-only (Node/Go tasks need their runtimes in the sandbox image); no sweep has been run on real GPU hardware yet, so `docs/benchmarks/latest.md` is not published until it has; no web UI comparison panel.*
- [x] **Phase 7 — Enterprise ease of use**: `keystone init`, `keystone doctor`, `keystone up`/`down`, `keystone bundle download-models|build-images|import`, `keystone ingest`, and the `keystone tenants`/`keystone users`/`keystone keys-create` admin commands are all real and done. `init` writes a real, working `.env` (from `.env.example`) with strong random secrets generated by default — not a separate `keystone.yaml` that would just be a second format to keep in sync, since `.env` (`src/config.py`) already is Keystone's one real config surface — and can interactively configure a git host and pick a model backend (self-hosted GPU or `benchmarks/frontier_proxy.py`). `doctor` then verifies what's actually reachable, independent of whether the app is even up yet. `up`/`down`/`bundle` are real subprocess wrappers (not reimplementations) around `docker compose`/`airgap/*.sh`, verified for real: `keystone up --dev` actually created real postgres/redis/qdrant containers via a real compose invocation. The admin commands (real HTTP wrappers around the existing root-admin-token-gated `/v1/admin` routes) create tenants, add/list users, and mint API keys — the first CLI-based bootstrap path this project has had; `scripts/create_api_key.py`'s interactive direct-DB-access script still exists alongside it. `ingest` is a real CLI wrapper around the existing `POST /v1/keystone/ingest` route (`src/memory/ingestion.py`'s `CodeIngestionPipeline`), closing the last gap this phase had. Verified for real against a live server and a real public GitHub repo: the first ingest processed 23 files into 61 chunks, and a second run against the same commit correctly reported all 23 files unchanged and 0 chunks re-created — the incremental skip path genuinely works, not just writes a row that claims it did. That same real run caught and fixed an actual bug: the ingest route didn't catch `InvalidRepositoryURLError` or git-clone failures, so a disallowed host or bad branch surfaced as an opaque 500 instead of the real reason — `src/api/routes/agents.py` now maps both to a clean 400 with the actual error message.
- [x] **Phase 8 — Public repository hygiene**: `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, `SECURITY.md`, issue/PR templates, CI (lint/type-check/tests/Helm lint+template/shellcheck/web build), CodeQL, and Dependabot are all real and green. The documentation site (`mkdocs.yml`, built `--strict` in CI) exists, with generated configuration/CLI/API references and a claims gate that ties documented sentences to collected tests; `keystone doctor` checks migrations, TLS, disk and readiness.
- [ ] **Phase 9 — Cost transparency + improvement suggestions**: the spend side is built — a durable per-tenant dollar ledger for gateway requests and agent tasks (`GET /v1/keystone/usage`, the web UI's Spend view), a monthly dollar budget per tenant enforced on the gateway and on task submission, routing decisions on every response, and time-to-first-token / upstream-error / budget metrics with alerts. *Still open: a pre-task cost estimate before a task starts, a per-task cost breakdown in the trace, and the evidence-backed suggestions engine.*

See `CHANGELOG.md` for what has already shipped. Contributions toward any unchecked item — or the noted gaps inside checked ones — are welcome; see `CONTRIBUTING.md`.
